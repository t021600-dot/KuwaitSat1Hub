## The mission I walked

Not a generic one. This exact one, because it is the one I will demo:

| | |
|---|---|
| **Title** | `Jahra plain — vegetation and surface temperature` |
| **Objective** | `Identify areas in Kuwait where increasing vegetation could improve environmental conditions. Focus on the plain south-east of Jahra: where would new planting actually lower local surface temperature over the next two years?` |
| **Area** | a box over the plain south-east of Jahra |

Checked by hand against the Kuwait box before going further: longitudes 47.60–47.74 sit inside

→ **in the build:** `03-security/db/06_validation.sql` → `kuwait_area_ok(jsonb)` and the

## 0 · The press — what the browser actually does

**IN:** a researcher, signed in, looking at `mission.html` for this mission, pressing
**Launch Mission**.

**BY HAND:** I acted as the browser. I wrote one line on the pad: *"tell the database this
mission should run."* That is genuinely all the browser gets to do, and it took me a minute to
accept it (see **U-6** below, where I wanted the button to call n8n directly).

**OUT:** one run id, back to the screen.

**THE ROW:**

```
mission_runs
  id                8d9b…  (uuid, generated by the database)
  mission_id        the Jahra mission
  status            'queued'
  started_at        now()
  finished_at       null
  tool_calls        0
  n8n_execution_id  null      ← never granted to the browser
  error_note        null      ← never granted to the browser
```

and on the mission itself: `status` → `'queued'`, `launched_at` → `now()`.

→ **in the build:** `03-security/db/05_views_rpc.sql` → `launch_mission(p_mission_id uuid)`,
granted to `authenticated` only. The panel calls it: `04-agents/app/agent-panel.js` →
`supabaseSource`. Table: `03-security/db/01_tables_rls.sql` → `public.mission_runs`.

**Noted while walking this:** `launch_mission()` refuses a second press while a run is
`queued` **or** `running` — *"This mission is already running."* So a run that is queued and
never collected blocks that mission forever. That is **O-3** at the bottom. It is a demo-night
hazard, not a design flaw.

## 0b · The pickup — where n8n comes in, and it is not where I expected

**IN:** nothing from us. n8n asks *us*.

**BY HAND:** I shuffled the pad to the other side of the desk to make the point to myself: the
browser has stopped. Nothing it did knows n8n exists. n8n polls for rows with
`status = 'queued'` and takes this one.

**OUT:** n8n holds a run id, and claims the run.

→ **in the build:** `04-agents/n8n/README.md`, node 2. **This node does not exist yet** — see
the honesty list. The rule it exists to satisfy is `03-security/docs/DECISIONS.md` **D-1**: no
webhook URL may appear in anything the browser downloads.

**Why this ordering matters for `au-m1`:** the judge's test is *close n8n completely, press the
button.* With the browser writing a row and n8n collecting it, closing n8n cannot break the
press — the row is written either way, and the run starts when n8n comes back. If the browser
called n8n, closing n8n would make the button fail in front of the judge. The security
constraint and the rubric test want the same shape, which is the single most reassuring thing I
found doing this.

**IN:** the mission area (the Jahra box), a cap of 20 scenes.

**BY HAND:** I opened the prototype's scene list and read off the scenes whose footprint

**OUT:** six scene references.

not refuse and it does not obey.

## 3 · Recommendation — first pass

**IN:** the four patches with their numbers.

**BY HAND:** I scored each one out of 100 on what I could *see*: how little canopy it has now,
how hot it runs, whether a truck can reach it. I did not think about the future at all, which
turns out to be the entire reason the decision point works (**U-4**).

**OUT:** four candidate zones, ranked:

| rank | zone | score | why it scored that |
|---|---|---|---|
| 1 | Zone A - North corridor | **88** | low existing canopy, road access on two sides |
| 2 | Zone B - Central basin | 81 | shallow depression retains runoff |
| 3 | Zone C - South flats | 67 | workable, higher soil salinity |
| 4 | Zone D - East margin | 59 | wind exposure needs a shelter belt |

No zone is under 40, so nothing is dropped before ranking.

**THE ROW:**

```
agent_steps
  step_name   'recommendation'
  tool        'zone_ranker.rank'
  arguments   { "candidates": 4, "excluded": 0 }
  allowed     true
  status      'complete'
```

**`excluded: 0` is there so the second pass can say `1`.** That one number is how a judge sees
the loop happened without reading any prose.

→ **in the build:** `steps.js` → `STEPS[2]`, flagged `loopTarget: true`; `run.js` → the
`push(logStep(runId, 'recommendation', { candidates: ranked.length, excluded: rejectedIds.length } …))`
*inside* `while (true)`. Ranking and the score floor: `decision.js` → `rankZones()`,
`MIN_ZONE_SCORE = 40`.

## 4 · Impact prediction — first pass

**IN:** the top-ranked zone only. Zone A.

**BY HAND:** different question, and this is the one I had to be careful about. Not *"how good
does this patch look"* but *"if we plant it, how much cooler is this spot in two years"*. For
Zone A: it is a corridor, it is narrow, it is open on both long sides, and the wind moves
through it. Most of the cooling blows away. I wrote **0.6 °C at 24 months** and sat looking at
it, because Zone A was my best-looking zone.

**OUT:** `Zone A → 0.6 °C projected cooling at 24 months`.

**THE ROW:**

```
agent_steps
  step_name   'impact_prediction'
  tool        'impact_model.project'
  arguments   { "zone": "z_a", "horizon_months": 24 }
  allowed     true
  status      'complete'
```

→ **in the build:** `steps.js` → `STEPS[3]`, flagged `decisionGate: true`; `run.js` →
`push(logStep(runId, 'impact_prediction', { zone: top ? top.id : null, horizon_months: 24 } …))`.

---

## ◆ THE DECISION — first firing. Zone A is refused.

**THE QUESTION, in the words I will say out loud:**

> Is the top-ranked zone's projected 24-month cooling at least **1.0 °C**?

**BY HAND:** 0.6 is less than 1.0. I have re-ranked **zero** times so far and the limit is two,
so I am allowed to go back. Zone A is struck off the list. The run goes back to step 3.

This is the moment the process stopped being a pipeline. Up to here I was doing steps in the
order I wrote them. Here, **the number step 4 produced chose what happens next** — and it chose
backwards.

**OUT:** verdict `rerank`, rejected zone `z_a`, and a sentence written for a researcher:

> `Zone A - North corridor projects only 0.6 °C of cooling at 24 months, below the 1.0 °C floor. Zone rejected. Ranking again without it.`

**THE ROW — and this is the row the whole item stands on:**

```
agent_steps
  step_name       'impact_prediction'      ← not a seventh name. see U-5
  tool            'impact_model.project'
  arguments       { "zone": "z_a", "projected_cooling_c": 0.6, "floor_c": 1.0 }
  allowed         FALSE
  refused_reason  'Zone A - North corridor projects only 0.6 °C of cooling
                   at 24 months, below the 1.0 °C floor. Zone rejected.
                   Ranking again without it.'
  status          'refused'                ← set by agent_log_step, not by us
```

Three things about this row that I only understood by writing it out:

1. **`allowed = false` is not an error.** The run is healthy. A refusal is a decision the agent
   made correctly, and it is the evidence the decision point is real.
2. **The reason goes in `refused_reason`, on the step.** Not in `mission_runs.error_note`.
   That was **U-1**, the first thing I got wrong.
3. **Both numbers being compared are in `arguments`.** 0.6 and 1.0, side by side on one row. A
   judge asking *"where did 0.6 come from"* gets pointed at a row, not at a paragraph. That is
   SHOULD item 11 falling out of the design for free, and I did not plan it.

→ **in the build:** `04-agents/agent/decision.js` → `decide()`, `IMPACT_FLOOR_C = 1.0`,
`MAX_RERANKS = 2`. The refused row: `run.js` → `if (verdict.verdict === 'rerank')`, then
`rejectedIds.push(...)`, `rerankCount++`, `continue;`. Status `'refused'` is set by
`agent_log_step`: `case when p_allowed then 'complete' else 'refused' end`.

**IN:** the surviving zones — B, C, D.

**BY HAND:** I drew three polygons on the printed map and wrote the rank, score and projected

results (3)  kind 'site'  · 'Zone D - East margin'  · Rank 3 of 3. Score 59/100. 0.9 °C.   ← see O-1

**THEN** the step row:

  step_name   'visualization'

`jsonb` and no bucket: `DECISIONS.md` **D-2**. Allowed kinds: `01_tables_rls.sql` →
`results.kind` CHECK.

# The six places I got stuck

The point of doing this on paper was to find these before they were code. Keeping them in, with
the wrong answer first, because the wrong answers are the useful part.

### U-1 · Where does the refusal text go?

**First answer:** `mission_runs.error_note`. It is right there, it is called error_note, done.

**Why it is wrong:** the browser has no grant on `error_note`
(`03-security/db/03_grants.sql` — it is marked INTERNAL in the table too). A reason written only
there is a reason the researcher **never sees**. I would have shipped a run that refuses
correctly and shows the user nothing, which is the `au-m2`/SHOULD-9 failure exactly.

**Resolved:** the reason is written as a **refused step** — `agent_log_step(..., p_allowed =>
false, p_refused_reason => '…')`. The `my_agent_steps` view exposes `refused_reason`, so it
reaches the screen. `error_note` still gets the text on a stall, as an internal record, but it is
never the only copy.

### U-2 · Second pass — overwrite step 3, or add another row?

**First answer:** overwrite, so the strip stays six clean steps.

**Why it is wrong:** that erases the only proof the decision did anything. Six tidy green rows
is exactly what a process with no decision point looks like.

**Resolved:** append. Two `recommendation` rows, two `impact_prediction` rows plus the refusal,
nine rows for a nine-step run. The panel collapses them for reading — *"Recommendation · ran 2
times"* — but the rows are all there underneath.
→ `04-agents/app/agent-panel.js`.

### U-3 · What does 0.95 do?

Caught this while writing 0.6 next to 1.0 and wondering where the edge is. The report prints
cooling to one decimal. So a zone at 0.9999 prints as **"1.0 °C"** and gets **refused for being
below 1.0** — the screen and the decision disagreeing, in front of a judge, with both numbers
visible.

**Resolved:** round to one decimal *before* comparing, so the printed number is the compared
number.
→ `decision.js` → `round1()`, used inside `decide()` before the `>=`.

### U-4 · Why does the loop ever stop?

I genuinely did not trust it. Going back to a step you already did is how you get an agent that
runs all night.

**Resolved, and this is the answer I say out loud:** it is not the same question twice.
Recommendation ranks on what was **observed**. Impact Prediction **models the zone forward 24
months** — information the ranking never had. And a refused zone **leaves the list**, so every
loop has one fewer zone. Four zones can loop at most three times on their own, and
`MAX_RERANKS = 2` stops it before that anyway. On the third refusal the run ends as `stalled`
with the reason on screen.
→ `decision.js` → `MAX_RERANKS`, and the `stall` verdict.

### U-5 · What is the refusal's step name?

I wanted to log it as `decision`. That is the honest name for it.

**Why it is wrong:** `agent_steps.step_name` has a CHECK constraint with exactly six names in it
(`01_tables_rls.sql`). A seventh name does not get logged — it throws.

**Resolved:** the refusal is logged under `impact_prediction`, which is correct anyway: the
decision is not a step, it is the **verdict on step 4's output**. And I decided I like the
constraint. The set of things this agent may claim to have done is fixed in the schema, not in
my workflow.

### U-6 · Why can't the button just call n8n?

It is one `fetch`. I wanted it.

**Why it is wrong:** that URL is then in View Source and in the Network tab, and n8n holds a key
that bypasses RLS. Anyone reading it can POST a run for any mission id.
(`DECISIONS.md` **D-1**.)

**Resolved:** the browser calls `launch_mission()` and writes a `queued` row; n8n polls. And the
thing I did not expect — this is also what makes `au-m1` pass. Close n8n, press the button, the
row is still written. The security rule and the rubric test wanted the same shape.

# What this walk found that is still open

Found by hand, **not fixed as of writing.** They go on Monday's list.

### O-1 · A zone under the floor is on the map

Zone D projects **0.9 °C** — under the 1.0 floor — and it still gets a `site` row and a polygon,
because the gate tests the **top-ranked zone only**. Meanwhile the `metric` row says *"Zones were
accepted only at or above 1.0 °C of projected 24-month cooling."*

Those two things cannot both be on screen. A judge who reads the map tooltip and then the metric
row catches us, and it would look like the guardrail is decorative.

**Pick one before Thursday, and say which:**
(a) drop zones under the floor from the written results and keep the sentence, or
(b) keep them as context and change the sentence to *"the recommended zone was accepted at or
above 1.0 °C; other candidates are shown with their own projections"*.

My preference is **(b)** — the rejected-zone story is better with the other numbers visible — but
either is fine and neither is done.
→ `04-agents/agent/run.js` → `accepted.forEach(...)` and the `'metric'` body.

### O-2 · Two coordinate orders in the repo, and nothing converts

- `01-front-end/app/js/seed.js:52` builds `polygon: [[y0, x0], …]` — **latitude first**, because
  that is what Leaflet's `L.polygon` takes (`01-front-end/app/mission.html:164`).
- `04-agents/app/demo.html:51` uses `[47.60, 29.40]` — **longitude first**, because that is
  GeoJSON.
- `run.js` wraps whichever it is given, unchanged: `{ type: 'Polygon', coordinates: [z.polygon] }`.

So `results.geometry` can be stored the wrong way round, and **nothing catches it** —
`kuwait_area_ok()` constrains `missions.area_geojson`, not `results.geometry`. On the map a
reversed Jahra polygon is 47° N 29° E, which is in Europe.

**Fix:** decide one order at the boundary — store GeoJSON `[lon, lat]`, flip once when handing
to Leaflet — and make the sample data agree.

### O-3 · A queued run that is never collected blocks its mission

`launch_mission()` refuses while a run is `queued` or `running`: *"This mission is already
running."* Nothing ages a queued run out. Press Launch with n8n not polling — which is the exact
state we are in tonight — and that mission cannot be launched again, on demo night, with no way
to clear it from the app.

Distinct from the relaunch rehearsal **R-1** in `GUARDRAILS.md`, which is about launching a
mission too *often*; this is about not being able to launch it at *all*. Both touch
`launch_mission()`, so ask Mariam once, not twice.

**Before demo night:** know the one-line SQL that clears a stuck queued run, and have it in the
runbook.
